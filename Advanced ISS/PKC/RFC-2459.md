## RFC-2459

**RFC-2459** is the original document that defined the profile of **X.509v3** as suggested by **PKIX** for use in Internet applications (e.g., IPsec, TLS, S/MIME). It provides interoperability guidelines for using X.509 certificates with standard internet mechanisms.

### Extensions
The extensions in RFC-2459 are defined by **OID (Object Identifier)**, which starts with the base:

`ID-PKIX ::= 1.3.6.1.5.5.7`  
(iso.org.dod.inet.sec.mechanisms.pkix)

The **OID** is a unique worldwide identifier used for data, originally introduced with **SNMP (Simple Network Management Protocol)**. OIDs are structured in a hierarchical manner and maintained by **IANA**. Every configuration element in network management (e.g., “activate interface n. 1”, “stop interface n. 2”) corresponds to an OID. All entities created by the PKIX group use the following branch of OIDs:

- `1 = iso` (top-level code)
- `3 = org` (organization within ISO)
- `6 = dod` (Department of Defense within the organization)
- `1 = inet` (related to the Internet)
- `5 = sec` (Security for the Internet)
- `5 = mechanisms` (specific security mechanisms)
- `7 = pkix`

This hierarchy can be represented by either numbers (used in certificates) or names for readability.

### Supported Algorithms
RFC-2459 also contains a list of supported algorithms, ensuring compatibility across different implementations.

### Implementation Suggestions
The document also provides practical implementation suggestions. One important example concerns the handling of **time and date** in certificates:

- **UTCtime** (Universal Time Coordinated) is mandatory to avoid issues with time zone differences when validating certificates.
- **Seconds** must always be included.
- **Zulu time** (Greenwich Mean Time, also known as **GMT** or +0) is mandatory for compatibility, especially with systems like Microsoft, which may not support other time formats.
- If the **year** is written using only two digits, it is interpreted as belonging to the interval **[1950, 2049]**.
    - For example, `51` is interpreted as **1951**, while `47` is interpreted as **2047**.
    - This approach stems from the practice of using only the last two digits of the year to save memory in certificates.

RFC-2459 ensures that these guidelines and specifications are followed to maintain consistency and interoperability across internet applications.



### Evolution of RFC-2459

**RFC-2459** was the original document defining the PKIX profile for X.509 certificates in Internet applications (e.g., IPsec, TLS, S/MIME). Over time, the PKIX profile evolved, and **RFC-2459** was eventually split into two parts:

- **RFC-3280**: This document defines the Internet profile for **Public Key Infrastructures (PKIs)**, covering X.509v3 certificates and X.509v2 Certificate Revocation Lists (CRLs). RFC-3280 later became obsolete and was replaced by **RFC-5280**, which continues to serve as the foundational specification for PKIX.
  
- **RFC-3279**: This document provides details on the algorithms (including their identifiers, parameters, and encodings) used within the PKIX profile defined in RFC-3280. By separating the algorithm specifications, RFC-3279 allows the algorithms to evolve independently from the core PKIX profile, making it easier to update them in line with the latest advancements in cryptography.

This separation allowed greater flexibility, particularly in updating the supported cryptographic algorithms, without having to revise the entire PKIX specification.
