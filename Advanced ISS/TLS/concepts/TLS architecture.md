
TLS can be used only on top of a **reliable transparent protocol** (TCP)

the unit of transmission for TLS is named **record** [[Advanced ISS/TLS/concepts/TLS record format|TLS record format]]

the **TLS record protocol** is an encapsulation protocol:
- used during the [[Advanced ISS/TLS/concepts/TLS handshake protocol|TLS handshake protocol]]
- used during an auxiliary protocol like [[Advanced ISS/TLS/concepts/TLS change cipher spec protocol|TLS change cipher spec protocol]]
- used during a (small) protocol [[Advanced ISS/TLS/concepts/TLS alert protocol|TLS alert protocol]]
- used to encapsulate application layer messages

**TLS session**:
- a logical association between client and server;
- created by the Handshake Protocol;
- defines a set of cryptographic parameters;
- is shared by one or more TLS connections (1:N);
- can’t be shared among different clients/servers;

**TLS connection**:
- a transient (specific) TLS channel between client and server;
- associated to one specific TLS session (1:1), i.e., a specific set of parameters;
- inside a connection, records are protected by the record protocol;


**Relationship among the keys and sessions**

When a new session is created (by performing the full [[Advanced ISS/TLS/concepts/TLS handshake protocol|TLS handshake]]), the so called **pre-master secret** (symmetric key) is generated by the client and sent to the server by using public key cryptography **PKC**.

This is common to several connections and remains the same during the whole session. The pre-master secret **is never used directly** for any cryptographic computation.

Every time a connection is created (including when the session is created for the first time), two random numbers are being generated, **client random** and **server random**.

If that's the *connection used to create the session* (first), then these numbers are used with the pre-master secret to generated the **master secret**. The master secret remains the same for the whole session and it's a sort of seed used by all connections in the same session to create different keys for MAC, encryption and IV if needed, for each connection (potentially 3 keys for each direction client to server and server to client, so 6 in total)


for *every connection*, the random numbers are used in combination with the master secret to generate new keys for the specific connection. In case of re-usage of a [[Advanced ISS/TLS/concepts/TLS handshake protocol|session-id]], the algorithms remain the same but the keys used for MAC and encryption are different.
